`cool-apisix` 提供 **APISIX 网关路由自动注册** —— 微服务启动时把自己的 gRPC 路由注册到
[Apache APISIX](https://apisix.apache.org/zh/)，网关统一对外暴露。

<Note>
  **按需引入**：只有依赖 `cool-apisix` 的微服务才会注册路由；未引入的服务不会有任何副作用。
</Note>

## 架构

```mermaid
flowchart LR
    C[客户端] -->|gRPC-Web / HTTP| A[APISIX :9080]
    A -->|/base.v1/*| B[base-service :8001]
    A -->|/dict.v1/*| D[dict-service :8002]
    A -->|/space.v1/*| S[space-service :8003]
    A -->|/task.v1/*| T[task-service :8004]
```

## 快速开始

### 1. 引入依赖

```toml
# apps/<name>/Cargo.toml
[dependencies]
cool-apisix = { workspace = true }
```

### 2. 启动时注册

```rust
// apps/<name>/src/main.rs
if let Err(e) = cool_apisix::auto_register(
    &cool_apisix::ApisixConfig::load(),
    "base-service",     // 服务 ID（路由资源 ID 前缀）
    "base.v1",          // proto 包名（匹配 /base.v1/*）
    8001,               // 监听端口
).await {
    tracing::warn!("apisix route register failed: {e}");
}
```

### 3. 配置

`apps/<name>/manifest/config.yaml`：

```yaml
apisix:
  enabled: true                              # 显式开启才注册
  adminUrl: "http://127.0.0.1:9180"          # Admin API 地址
  adminKey: "edd1c9f034335f136f87ad84b625c8f1"
  upstreamHost: "127.0.0.1"                  # 本服务对外可达地址
  scheme: "grpc"                             # gRPC 代理
  prefix: "cool"                             # 路由 ID 前缀
```

或用环境变量：

```bash
export APISIX_ADMIN_URL=http://127.0.0.1:9180
export APISIX_ADMIN_KEY=your-admin-key
export APISIX_ENABLED=true
```

## API

<AccordionGroup>
  <Accordion title="auto_register(cfg, service_id, package, port)">
    **推荐入口**。自动构造路由：ID = `{prefix}-{service_id}`，
    URI = `/{package}/*`，上游 = `{upstream_host}:{port}`。

    ```rust
    cool_apisix::auto_register(&cfg, "dict-service", "dict.v1", 8002).await?;
    ```
  </Accordion>

  <Accordion title="register_routes(cfg, routes)">
    批量注册自定义路由（PUT 幂等 upsert）。

    ```rust
    let route = cool_apisix::ServiceRoute {
        id: "custom-route".into(),
        name: "自定义路由".into(),
        uris: vec!["/my.api.v1/*".into()],
        upstream_addr: "10.0.0.5:9000".into(),
        scheme: "grpc".into(),
        priority: 10,
        labels: Default::default(),
    };
    cool_apisix::register_routes(&cfg, &[route]).await?;
    ```
  </Accordion>

  <Accordion title="deregister_route(cfg, route_id)">
    删除路由（服务下线时调用）。

    ```rust
    cool_apisix::deregister_route(&cfg, "cool-base-service").await?;
    ```
  </Accordion>
</AccordionGroup>

## APISIX Admin API 说明

| 项目 | 值 |
| --- | --- |
| 默认地址 | `http://127.0.0.1:9180/apisix/admin` |
| 认证 | `X-API-KEY: {admin_key}` |
| 注册方式 | `PUT /apisix/admin/routes/{id}`（幂等 upsert） |
| 路由匹配 | `uris: ["/package/*"]`（Ant 风格） |
| gRPC 代理 | `upstream.scheme: "grpc"` |

<Warning>
  APISIX 3.19 校验：`uri` 与 `uris` **二选一**，不能同时出现。本 crate 只写 `uris`。
</Warning>

## 多实例自动发现

同一服务启动多个实例时，APISIX **自动合并上游节点**，无需手工配置负载均衡：

```mermaid
flowchart LR
    C[客户端] --> A[APISIX :9080]
    A --> B1[base :8001]
    A --> B2[base :8011]
    A --> B3[base :8021]
```

```bash
# 实例 1
MICRO_CONFIG=apps/base/manifest/config.yaml ./target/debug/base-service  # :8001
# 实例 2（不同端口）
MICRO_CONFIG=apps/base/manifest/config.yaml   MICRO_SERVER__ADDRESS=0.0.0.0:8011 ./target/debug/base-service
# 实例 3
MICRO_CONFIG=apps/base/manifest/config.yaml   MICRO_SERVER__ADDRESS=0.0.0.0:8021 ./target/debug/base-service
```

**节点管理**：

| 操作 | 行为 |
| --- | --- |
| 实例启动 | GET 现有节点 → 合并自己 → PUT（幂等） |
| 实例下线 | 摘除自己的节点；若已无实例则删除路由 |

```rust
// 多实例注册（推荐）
let inst = cool_apisix::ServiceInstance {
    service_id: "base-service".into(),
    package: "base.v1".into(),
    addr: "host.docker.internal:8001".into(),
};
cool_apisix::register_instance(&cfg, &inst).await?;

// 实例下线时摘除
cool_apisix::deregister_instance(&cfg, &inst).await?;
```

实测（3 实例注册后摘除 1 个）：

```json
{
  "nodes": {
    "host.docker.internal:8021": 1,
    "host.docker.internal:8001": 1
  }
}
```

## 故障转移与健康检查

上游自动配置 **retries + 主动/被动健康检查**，实例宕机时请求自动切换：

```yaml
upstream:
  type: roundrobin
  retries: 2                    # 失败自动重试到其他节点
  checks:
    active:                     # TCP 主动探测（2s 间隔）
      type: tcp
      healthy:   { interval: 2, successes: 1 }
      unhealthy: { interval: 1, failures: 2 }
    passive:                    # 被动探测（基于请求失败）
      healthy:   { successes: 3 }
      unhealthy: { http_failures: 2, tcp_failures: 2 }
```

### 实测：异常宕机（kill -9 不摘除节点）

```text
kill -9 :8012（无 deregister，APISIX 节点表仍含死节点）

立即压测 20 次    → 20/20 成功 ✅（retries 立即兜底）
健康检查收敛后 20 次 → 20/20 成功 ✅（死节点已隔离）
流量分布          → :8002 → 21  :8022 → 19
```

### 实测：实例重启自动恢复

```text
重启 :8012 → 健康检查探测成功 → 自动重新分担流量

压测 60 次 → 60/60 成功
流量分布  → :8002 → 18  :8012 → 20  :8022 → 22
                                                ↑ 重启实例恢复分载
```

### 完整故障转移周期

```text
① 3 实例均衡      18 / 20 / 22  ✅
② 优雅下线 :8012  20/20 成功     ✅  节点立即摘除
③ 异常宕机 :8022  40/40 成功     ✅  retries + 健康检查隔离
④ 重启 :8012      60/60 成功     ✅  自动恢复，流量重新均衡
```

### 实测：滚动更新（逐个重启，持续压测）

```text
后台持续压测（50ms 间隔）+ 逐个滚动重启 3 实例

:8002 更新  累计 OK=117 FAIL=0
:8012 更新  累计 OK=204 FAIL=0
:8022 更新  累计 OK=290 FAIL=0
最终结果    总请求 369 · 成功 369 · 失败 0 · ✅ 零失败
```

滚动更新流程（每实例）：

```text
deregister_instance → kill 旧进程 → 启动新进程 → register_instance
```

### 下线与恢复方式对比

| 场景 | 行为 | 结果 |
| --- | --- | --- |
| **优雅下线** | `deregister_instance` → 进程退出 | 节点立即摘除，100% 成功 |
| **异常宕机** | `kill -9`（无摘除） | retries 兜底 + 健康检查隔离，100% 成功 |
| **实例重启** | 重新启动进程 | 健康检查自动恢复，流量重新均衡 |
| **滚动更新** | 逐个重启全部实例 | **全程零失败**（369/369） |

<Note>
  优雅下线推荐在进程退出钩子中调用 `deregister_instance`；
  即使遗漏，健康检查 + retries 也能保证零失败。
  实例重启**无需任何手工干预**，健康检查自动重新纳入。
</Note>

## 慢实例（响应超时）检测与摘除

### 健康端点

每个微服务内置 HTTP 健康端点（`grpc_port + 10000`）：

```bash
curl http://127.0.0.1:18002/health   # 快实例 → 200 (20ms)
curl http://127.0.0.1:18012/health   # 慢实例 → 超时 (1016ms) ← 可被探测
```

混沌测试注入：`COOL_TEST_RESPONSE_DELAY_MS=2000` 使响应延迟 2s。

### 实测结果

```text
A. 慢实例在环（retries 兜底）
   20 请求 → 15 成功 / 5 失败   ← 超时窗口内仍有失败

B. 健康信号检测 → 摘除慢实例
   20 请求 → 20 成功 / 0 失败   ✅ 零失败
```

| 阶段 | 成功率 | 说明 |
| --- | --- | --- |
| 健康探测 | — | 慢实例 1016ms 超时被识别 |
| 慢实例在环 | 75% | retries 兜底，超时窗口仍有失败 |
| **健康信号摘除后** | **100%** | 流量全部走快实例 |

### APISIX 限制与生产建议

<Warning>
  **APISIX 的 TCP 主动检查无法感知慢实例**（端口开放即判健康），
  且 `checks.active.port` 为全局配置，不支持逐节点健康端口。
  因此「响应超时」型故障需依赖**外部编排器**（K8s / Consul）的健康检查摘除节点。
</Warning>

| 方案 | 检测能力 | 推荐场景 |
| --- | --- | --- |
| APISIX TCP check | 存活（进程崩溃） | 基础故障 |
| APISIX passive check | 连接失败 | 网络故障 |
| **HTTP 健康端点**（本方案） | **响应超时 / 依赖故障** | **慢实例检测** |
| K8s readiness probe | 同上 | **生产推荐** |

**生产推荐部署方式**：

```yaml
# K8s Deployment —— 就绪探针检测慢实例
readinessProbe:
  httpGet:
    path: /health
    port: 18001        # grpc_port + 10000
  timeoutSeconds: 1
  failureThreshold: 2
# 就绪失败 → 从 Endpoints 摘除 → APISIX 不再路由
```

## 假死实例（不响应不报错）兜底

模拟方式：`SIGSTOP` 冻结进程（状态 `T`），接受不了连接也不返回错误：

```bash
kill -STOP <pid>   # 假死
kill -CONT <pid>   # 恢复
```

### 实测结果

```text
假死 :8012 在环，经网关压测 30 请求

成功: 30/30  失败: 0/30  ✅ 零失败
流量分布: :8002 → 38  :8022 → 28   ← 全部走健康实例

健康探测: :18012 → 2017ms 超时   ❌ 可被识别
SIGCONT 恢复后: 20/20 成功        ✅
```

### 超时兜底机制

| 层级 | 机制 | 作用 |
| --- | --- | --- |
| 连接层 | `timeout.connect: 1s` | 假死实例 TCP 握手超时 |
| 重试层 | `retries: 2` | 自动换健康节点 |
| 健康层 | HTTP `/health` | 编排器摘除假死节点 |

### 三类故障对比

| 故障类型 | 现象 | 兜底机制 | 成功率 |
| --- | --- | --- | --- |
| **进程崩溃** | 连接拒绝 | retries + 健康检查 | 100% |
| **响应超时** | 慢响应 | retries + 健康端点 | 100%（摘除后） |
| **假死** | 不响应不报错 | **connect 超时 + retries** | **100%** |

<Note>
  假死（SIGSTOP）场景下，TCP 连接无法建立 → `connect` 超时 → `retries` 立即换节点，
  因此**无需等待健康检查收敛即可 100% 成功**，是三类故障中兜底最彻底的场景。
</Note>

## 资源耗尽 / 降级熔断

### 混沌注入手段

```bash
# CPU/内存打满（后台线程）
COOL_TEST_CHAOS_CPU_THREADS=16 COOL_TEST_CHAOS_MEM_MB=2048 ./dict-service

# 请求级阻塞（模拟线程池耗尽 / handler 卡死）
COOL_TEST_CHAOS_BLOCK_MS=2000 ./dict-service
```

### 实测矩阵

| 场景 | 现象 | 结果 |
| --- | --- | --- |
| **CPU/内存打满**（16 线程 + 2GB） | CPU=775%，RSS 爬升 | **30/30 成功** —— tokio I/O 服务天然抗压 |
| **阻塞 < 读超时**（2s block，timeout=30s） | 响应变慢 | **30/30 成功** —— 降级但可用 |
| **阻塞 > 读超时**（2s block，timeout=1s） | 响应超时 | **19/30 成功** —— 超时失败，retries 部分兜底 |
| **健康信号熔断摘除** | 节点移除 | **20/20 成功** ✅ 零失败 |

### 超时阈值 = 熔断边界

```text
handler 阻塞时长 vs timeout.read 决定熔断行为：

  阻塞 < timeout  → 请求排队等待，成功（降级可用）
  阻塞 > timeout  → 504 超时，retries 换节点
  持续超时         → 健康端点探测超时 → 摘除节点
```

**生产建议**：`timeout.read` 设为 SLA 上限（如 1s），超过即触发熔断链路。

### 健康端点同步感知

健康端点与 handler 共享阻塞状态（`COOL_TEST_CHAOS_BLOCK_MS`）：

```text
:18002 → HTTP 200  14ms    ✅ healthy
:18012 → 1017ms 超时       ❌ 降级实例可被识别
:18022 → HTTP 200  13ms    ✅ healthy
```

### 熔断降级完整链路

```text
① handler 阻塞 > timeout        → 504 超时
② retries: 2                    → 换节点重试（部分兜底）
③ 健康端点超时                  → 外部健康检查识别
④ deregister / K8s 摘除          → 流量全部走健康实例（零失败）
```

<Note>
  APISIX 被动健康检查对 gRPC 读超时不敏感；「响应超时」型熔断依赖
  **超时阈值 + retries + 外部健康检查**（K8s readinessProbe）组合。
  CPU/内存打满对 I/O 密集服务影响有限，真正降级源于 **handler 阻塞**（线程池/锁竞争）。
</Note>

## gRPC 与 gRPC-Web 双路由

原生 gRPC 与浏览器 gRPC-Web **分离注册**（避免 grpc-web 插件干扰原生 HTTP/2）：

| 协议 | URI 模式 | 插件 | 用途 |
| --- | --- | --- | --- |
| 原生 gRPC | `/base.v1.*` | proxy-rewrite | grpcurl / 服务间调用 |
| gRPC-Web | `/web/base.v1.*` | proxy-rewrite + grpc-web | 浏览器前端 |

gRPC-Web 路由通过 `regex_uri: ["/web/(.*)", "/$1"]` 剥离前缀后转发。

```bash
# 原生 gRPC
grpcurl -plaintext localhost:9080 base.v1.BaseOpenService/Captcha

# gRPC-Web（浏览器）
curl -X POST http://localhost:9080/web/base.v1.BaseOpenService/Captcha \
  -H "Content-Type: application/grpc-web+proto" -H "X-Grpc-Web: 1"
```

## 设计要点

| 特性 | 说明 |
| --- | --- |
| **按需引入** | 未依赖 `cool-apisix` 的服务零副作用 |
| **幂等 upsert** | PUT 重复执行安全，服务重启自动刷新路由 |
| **gRPC 代理** | `scheme: grpc` + `/package/*` 匹配全部 RPC |
| **失败不阻断** | 注册失败仅告警，服务照常启动 |
| **标签管理** | `managed-by: cool-apisix` 便于批量运维 |
| **双协议路由** | 原生 gRPC + gRPC-Web 分离，`/web/` 前缀 + 路径重写 |
| **多实例自动发现** | 节点合并/摘除，APISIX roundrobin 天然负载均衡 |
| **自动故障转移** | retries + 主动/被动健康检查，宕机零失败 |
| **慢实例检测** | HTTP 健康端点（grpc+10000），供 K8s/APISIX 探测 |

<Note>
  生产环境务必更换默认 Admin Key，并限制 `allow_admin` IP 白名单。
</Note>
